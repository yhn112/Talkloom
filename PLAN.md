# Transcriber — project plan

A local meeting transcriber for macOS: a menu-bar app that records the microphone and
system audio during any call (Zoom, Meet, Telegram — anything), transcribes locally with
Whisper and optionally through a cloud API, attributes speakers, and writes a summary.
Meetings are in Russian and English, often mixed.

## How existing products work

There are two ways to capture meeting audio:

1. **A bot participant** (Otter, Fireflies) joins the call as an attendee and receives
   per-participant tracks and speaker names from the meeting API. It needs server
   infrastructure — a container per meeting — and everyone can see the bot. *Not our path.*
2. **Local capture** (Fathom, Granola, and similar macOS apps) records the microphone and
   system audio on the user's machine. It works with any calling service, stays private,
   and runs offline. *This is our path.*

Nearly every open-source implementation then follows the same pipeline:

```
audio → VAD → ASR (Whisper: text + word timestamps)
      → diarization (pyannote / voice embeddings)
      → align words to speakers
      → LLM: summary, action items
```

The decisive advantage of local capture is that microphone and system audio are two
separate channels, which is free first-level diarization: "me" versus "everyone else",
with no model and no error. Within the system channel, individual speakers can be
separated later by clustering voice embeddings.

## Architecture

```
┌─ macOS app (Swift / SwiftUI, menu bar) ──────────────────────────┐
│                                                                  │
│  Capture                                                         │
│   ├─ AVAudioEngine (microphone, Voice Processing IO for AEC)     │
│   └─ CoreAudio process tap (system audio)                        │
│         ↓  two native-rate mono Int16 master tracks on disk      │
│  ASR (protocol Transcriber, two implementations)                 │
│   ├─ Local: whisper.cpp (Metal) or WhisperKit (CoreML)           │
│   └─ Cloud: OpenAI / Deepgram, opt-in                            │
│         ↓  segments with timestamps                              │
│  Diarization: v1 = channel of origin; v2 = embedding clustering  │
│  within the system channel                                       │
│         ↓                                                        │
│  Summary: LLM (Claude API, or Ollama for fully offline)          │
│         ↓                                                        │
│  Storage: SQLite (+ FTS5 for search), Markdown export            │
└──────────────────────────────────────────────────────────────────┘
```

The stack is **Swift throughout**. Audio capture on macOS is only reachable from native
code, and shipping a Python sidecar for faster-whisper/pyannote would make packaging
painful. whisper.cpp and CoreML diarization keep the ML side inside one binary.

Build tooling: the project is described in `project.yml` and generated by XcodeGen, then
built with `xcodebuild`. Signing uses a local self-signed certificate so TCC grants
survive rebuilds.

## Stages

### Stage 0 — skeleton
- SwiftUI menu-bar app with a start/stop control.
- Request permissions: microphone, and system audio capture (`kTCCServiceAudioCapture`).
- Verify that CoreAudio process taps avoid the Screen Recording prompt entirely.

### Stage 1 — audio capture
- Microphone via `AVAudioEngine` with Voice Processing IO, so speaker output doesn't
  echo back into the mic track and duplicate every line.
- System audio via `AudioHardwareCreateProcessTap` plus an aggregate device
  (available since macOS 14.2).
- Write two files in the device's own format; resampling to 16 kHz happens later, over
  the finished file, never on the audio path.
- Known traps, all of which present as a valid file rather than as an error: Voice
  Processing IO reports nine channels where the device has one; automatic ducking quiets
  the other participants unless `voiceProcessingOtherAudioDuckingConfiguration` disables
  it; an aggregate device that contains the output device as well as the tap delivers two
  streams and the tap is not the first; a tap that has died goes on producing a valid,
  silent file. See `docs/system-audio-capture.md` for the measurements.
- Still open: a recording interrupted by a crash or a kill leaves WAV headers claiming
  zero bytes, so the tracks read as empty even though the samples are on disk. The sizes
  can be recovered from the file length; do it on launch for any session without a
  `session.json`.
- ✅ Done when: after a call, two clean tracks exist on disk, verified by measured peak
  amplitude on each — not by file size.

### Stage 2 — offline transcription (MVP)
- whisper.cpp with Metal, or WhisperKit; a `large-v3`-class model, which is what Russian
  needs — small models degrade far more on Russian than on English.
- Silero VAD ahead of ASR. This is mandatory, not cosmetic: on silence Whisper emits
  confident hallucinations lifted from training subtitles.
- Derive the 16 kHz mono tracks from the masters with `afconvert` before transcribing.
- Transcribe both tracks after the meeting; merge by timestamp, labelling mic segments
  "me" and system segments "them".
- A `Transcriber` protocol with a second, cloud-backed implementation behind a setting.
- ✅ Done when: record a call → get a transcript with speaker labels, measured on the
  Russian and English fixtures.

### Stage 3 — summaries and storage
- LLM provider selectable: Claude API for quality, Ollama for fully offline.
- Prompt produces summary, action items, and decisions, in the meeting's language.
- SQLite with FTS5: meeting list, full-text search, Markdown export.

### Stage 4 — live transcription
- Sliding window with overlap so words aren't cut at chunk boundaries; cutting on
  VAD-detected pauses is more reliable than cutting on a timer.
- Later: a small model for a live draft, with a large model re-run after the meeting.

### Stage 5 — full diarization
- Cluster voice embeddings within the system channel (FluidAudio, a Swift/CoreML port of
  pyannote, or CAM++ embeddings) to produce "Speaker 1 / Speaker 2 / …", renameable in the UI.

### Stage 6 — polish
- Detect an active call (Zoom, Meet, FaceTime) and offer to record.
- Model settings, history, cross-meeting search, sharing.

## Risks

Concrete capture correctness and simplification work discovered during implementation is
tracked in [`docs/technical-debt.md`](docs/technical-debt.md). Resolve its P0 items before
building Stage 2 on top of the recorded timeline.

- **Process tap behaviour under device changes** is the least documented part of the
  capture path; budget time for it.
- **Whisper hallucinations on silence** — VAD is the mitigation, plus filtering on
  log-probability and compression ratio.
- **Mixed Russian and English within one meeting** — Whisper detects language per chunk,
  so detection oscillates; if it hurts, force the language per meeting.
- **A `large-v3` model needs roughly 3 GB of RAM** — make model size configurable.
